> 状态：**已实现**（`src/features/AutoImport/`，随应用发布）。

## 零、这个功能要解决什么

现有「批量导入」的语义是**只增不改**：

- `core/ops/batch.js` 的 `batchAddPNodes` 只会 `push` 新节点；
- `core/validate/conflict.js` 的 `collectBatchConflicts` 发现重名**只提示，然后重命名**（`demo` → `demo1`）。

所以同一份数据导两次，你会得到一堆 `demo1`、`demo2`……它不是一个能反复运行的同步机制。

**本功能要做的是**：外部脚本爬取 → 转成约定的导入包 → 一次性**增量合并**进主树，
并且**反复运行结果收敛**（第二次运行应当是 no-op）。

---

## 一、三条根因判断

这三条决定了后面所有设计，先看它们。

### 1.1 查重的身份不能来自应用内部

`node.id` 由 `utils/id.js` 生成：

```js
'n_' + (++AppState.meta.idCounter) + '_' + Date.now().toString(36)
```

它**跨机器、跨会话都不稳定**。把它写进爬虫的输出里，换台机器或清一次数据就全失配。

→ **身份必须由爬虫侧提供。** 这是本设计的根基。

### 1.2 「同父节点下 problemId 唯一」不是身份

现有查重用的是「同一父节点下 `problemId` 不重复」。那只是**展示名约束**，
不是身份：

- 改了题号 → 认不出来，造重复；
- 同一场比赛里两个题号都叫 `A`（不同场次合到同一容器）→ 误判冲突。

→ **身份与显示解耦**：身份用外部键（`extKey`），`problemId` 回归纯展示槽位。
（早期设计还留了"题号兜底匹配"这一级，现已删除——见 4.2。）

### 1.3 增量 = 合并，就必须有逐字段策略

爬虫数据必然有错（难度估算、通过率漂移、标题时有时无）。
如果直接覆盖，**你手填的 `remark` 题解会被冲掉**——而 `remark` 是这个应用里
**唯一不可再生**的数据（难度状态可补录，思路忘了就没了）。

→ **绝不无条件覆盖**。逐字段策略是硬需求，不是锦上添花。

## 二、寻址模型：怎么指定「加到哪里」

**成熟格式的形态：每条记录自带「节点类型 + 应上接节点的 extKey」。**

```json
{
  "节点类型": "P",
  "extKey": "qoj:4113:20236",
  "父extKey": "qoj:4113",
  "题号": "A",
  "题目名称": "All Closed"
}
```

**这推翻了早期设计里的"路径字符串"，而且更好：**

| | 路径字符串（已废弃） | 类型 + 父 extKey（现行） |
|---|---|---|
| 转义地狱 | 名称里的 `/`、`]` 要转义 | **不存在** |
| 层级表达 | 语法 | **结构**（`parentExtKey` 是数据） |
| C/P/R 混合 | 拼路径很别扭 | **天然支持**，就是同一个扁平数组 |
| 校验 | 解析字符串 | 查引用是否存在 |

### 2.1 三个字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `节点类型` | ✅ | `O` / `W` / `S` / `C` / `P` / `R`（字母码，与 `TYPE_CHILDREN_MAP` 一致） |
| `extKey` | ✅ | 该节点的**全局唯一**身份（见 2.4） |
| `父extKey` | ❌ | 留空 / 省略 ⇒ 挂根（3.3）；非空时必须是父节点身份 |

### 2.2 解析算法

```
1. 收集包内全部记录的 extKey，建立索引
2. 拓扑排序（父必须先于子；成环或引用不存在 → 逐条报错）
3. 逐条解析父容器：
     父在包内   → 用包内该记录的节点（同批创建或复用）
     父在树上   → 按 extKey 全局查找
     两边都没有 → ⛔ 拒绝该条（见 2.3）
4. 校验父节点类型允许该子类型（查 TYPE_CHILDREN_MAP）
5. node.extKey === record.extKey → 合并**字段**（**并按 `parentExtKey` 换父**，见下）；否则新建
```

> **位置也以记录为准**：已有节点若挂在别的父下，导入会**换父**（同级顺序 = 挂到新父末尾）。
> 理由：应用里**没有**别的换父入口（只有同级上移/下移）⇒ 记录的 `父extKey` 是位置的唯一真源；
> 否则脚本侧的落位改动（`scripts/nature-rehome.mjs`）在应用里永远看不见。
> 预览里单列一栏 **`🔀 重挂 N`**（`plan.summary.moved`），记录表里那些行尾部带 `🔀`。

**因为父引用是数据，C/P/R 混合不需要任何特殊处理**——
它们只是同一个数组里 `节点类型` 不同的记录，拓扑排序自然会把
C 排在 P 前面、P 排在 R 前面。

### 2.3 容器可以不在包里，但必须在树上 ⚠️

**允许两种来源**：包内自带，或树上已有（带对 `extKey`）。

| 情况 | 行为 |
|---|---|
| 父在包内 | ✅ 用包内的（可能同批创建） |
| 父在树上（`extKey` 命中） | ✅ 复用 |
| **两边都没有** | ⛔ **拒绝该条**，报错 |

**明确不做隐式创建，也不从 URL 推断。** 理由：

- 隐式创建违反 4.4「必须有 extKey」——凭空造一个容器，它的 `extKey` 从哪来？
- 从 `题目链接` 正则提取 contest id 会把**平台 URL 规则塞进应用**，违背"应用不猜"。

> ⚠️ **实践后果**：`qoj_problems.json` 这类**只有 P、没有 C** 的包，
> 首次导入会**整批拒绝**，因为树上还不存在 `qoj:4113` 那个比赛。
> 有两条出路：
> 1. **推荐**：先跑一次「比赛批量导入」把 C 建出来（决策 2 的独立入口），
>    再跑题目包；
> 2. 或让爬虫在题目包里**顺带输出一条 C 记录**（同一个数组，`节点类型: "C"`）。
>
> 这正好实现你要的「比赛也可能批量导入」。

### 2.4 `extKey` 必须全局唯一（约束升级）⚠️

早期设计只要求「同容器唯一」。**用 `parentExtKey` 查找父节点后，这条不够了**：

> 若两棵子树下各有一个 `qoj:4113`，父引用就有歧义。

→ 约束升级为**全局唯一**。由 `core/validate/upsertConflict.js` 的
`collectExtKeyConflicts(state)` 检查**树上已有的**冲突（**跨容器同 key 也算**）；
**同一个包里**的重复是另一个函数：`collectBatchExtKeyConflicts(records)`。

这也让查找退化成一次哈希表查询，无需遍历容器。

### 2.5 容器链必须合法：`O → W → S → C → P → R` ⚠️

**这是实现期发现的一处设计文档错误，必须显式记下来。**

`core/model/constants.js` 的约束是：

```js
TYPE_CHILDREN_MAP = {
    'O': ['W', 'S'],
    'W': ['S', 'W'],   // ← 注意：没有 C
    'S': ['C', 'S'],
    'C': ['P'],
    'P': ['R'],
    'R': []
};
```

**平台（W）下不能直接放比赛（C）**，比赛必须挂在**系列（S）**下。

早期版本的本文档在本节和 7.1 的示例里写成了 `W → C`，那是**不合法的**，
`core/ops/upsert.js` 会以 `bad-parent-type` 正确拒绝它（已由单测覆盖）。

**对 qoj 的实际影响**：qoj 本身没有"系列"这一层概念，
所以它的容器链必须**插入一个 S 层**：

```
O → W[qoj] → S[比赛分组] → C[qoj:4113] → P[…] → R[…]
```

S 层的名字由爬虫给（如 `QOJ Contest`，或按年份/赛制分组）。
这是**记录在案的设计后果**，不是 bug——若要省掉这一层，
需要改 `TYPE_CHILDREN_MAP`（`W` 加 `C`），而那会连带
`docs/guide.html` 的树结构约束表与 `src/test/model.test.js` 的断言，
属于**独立的架构决策**，不在本功能范围内。

> 迁移备忘：层级图（`W 平台 ──→ W(平台) / S(系列)`）与代码一致，
> **是本文档早期版本画错了**。

### 2.6 核心存储：`node.extKey`

`extKey` 是**新字段**，用插件的 `registerNodeMigration` + `registerVNodeMigration` 补齐
（插件加字段是受支持的）。

**不覆盖任何结构字段**（`STRUCTURAL_VNODE_KEYS`）。

**应用不解析 `extKey` 的内部结构**，只当作不透明字符串比较——
各平台可以有自己的命名习惯。建议格式：

| 平台 | 建议 |
|---|---|
| qoj | 题目 `qoj:4113:20236`，比赛 `qoj:4113`，提交 `qoj:sub:2951241` |
| codeforces | 题目 `cf:1920.A`，比赛 `cf:1920`，提交 `cf:sub:123456789` |

完整拼法与理由见 **3.4**。

> 需要在 `A_registry.js` 登记吗？**不用**。`nodes` 是整体持久化/导出的，
> `extKey` 挂在 `node` 上会自动进快照、持久化与导出。
> （`A_registry.js` 是按**顶层字段**登记的，节点内部字段不单独登记。）

## 三、身份模型：`extKey`

成熟格式里，**身份由爬虫直接给出**，不再有"应用根据 `ext` 子对象推导"这一步：

```json
{
  "节点类型": "P",
  "extKey": "qoj:4113:20236",
  "父extKey": "qoj:4113"
}
```

| 字段 | 说明 |
|---|---|
| `extKey` | **该节点自己的**身份，全局唯一，直接写到 `node.extKey` |
| `父extKey` | **父节点的**身份，用于解析挂接位置 |

**应用不做任何推导。** 早期设计里的 `ext = { platform, contestId, problemIndex, externalId }`
四件套**整块删除**——成熟格式把这件事上推给了爬虫，应用侧因此少一层易错的规范化逻辑。

### 3.1 唯一要求：非空

`extKey` 的唯一硬要求是**非空**（`trim` 后非空字符串）：

```
extKey 非空字符串  →  使用
否则              →  ⛔ 拒绝该条（见 4.4）
```

**应用不校验、也不解析它的内部结构。** 格式规范由你（爬虫侧）负责——
这与"警告多是你自己的问题"是同一个立场：应用只管它是不是空的、重不重复。

### 3.2 应用只做两项检查（都是硬错误）

| 检查 | 位置 |
|---|---|
| 同一份包内 `extKey` 重复 | `resolve.js`（逐条报错 —— **不经过 plan.js**；plan.js 的注释也说明了这点） |
| 与树上已有节点 `extKey` 冲突但父容器不同 | `core/validate/upsertConflict.js` 的 `collectExtKeyConflicts`（由 `plan.js` 第 1 步调用） |

> 注意第二项不是"拒绝"——它意味着**你想把同一个 key 挂到两个不同位置**，
> 这是数据错误（全局唯一约束，见 2.4）。

### 3.3 根节点规则 ⭐

**两条都支持**：

```
父extKey 为空串 / null / 省略  →  父 = state.rootId          （隐式，推荐）
父extKey = 根节点的 extKey      →  也能解析到根               （显式，可选）
```

**推荐用隐式**（留空）：平台的记录直接省略 `父extKey`，语义无歧义——
**空 ≠ 任何合法 extKey**。爬虫也不必知道应用侧的 `state.rootId`。

**但根节点现在也可以有 `extKey`**（早先版本不允许，已在实现期放开）：

- 用途：脚本可以**显式**指向根（`父extKey = <根key>`），
  不必依赖"留空 = 挂根"这条约定；
- 设置入口：文件夹视图 `🔑 补身份键` 页顶部那块「**根节点的 extKey**」表单——
  根节点**不是任何节点的子节点**，不会出现在下面的子节点列表里，
  所以必须有这块单独的表单才够得着它；
- 语义与其它节点一致：**只补空的**；已有值要改需二次确认（单向操作）。

> 注意：根节点的 `extKey` **不参与**导入时的父引用解析——
> 解析只查 `state.nodes` 里的普通节点（见 2.2），
> 根是通过"空父引用"或"命中根 key"两条路进入的。

### 3.4 `extKey` 拼法约定（推荐，非强制）⭐

**这份约定是给爬虫的"照着抄"清单，应用不解析、也不校验它**（见 3.1）。
定这套是为了让 key **可读、可排查、且能一眼看出层级**。

**语法**：`<平台码>:<类型码>:<平台内稳定ID>`
`<类型码>` 用应用自己的单字母（`W`/`S`/`C`/`P`/`R`）。
比赛节点可省略 `<类型码>`（见下），提交用 `sub` 防止与题目撞。

**层级关系靠 key 前缀自然嵌套**：某个节点的 key 就是它的父 key 加一段。
这让"父引用漏写"时你一眼能看出来。

#### qoj（按现有两个样本文件）

> ⚠️ **必须插一个 `S` 层**：`W` 下不能直接放 `C`（见 **2.5**），
> 而 qoj 没有"系列"概念，所以容器链是
> `qoj → qoj:contest → qoj:4113`。

| 节点 | `节点类型` | `父extKey` | `extKey` | 爬虫从哪拿 |
|---|---|---|---|---|
| 平台 | `W` | （省略 → 根） | `qoj` | 常量 |
| 比赛分组 | `S` | `qoj` | `qoj:contest` | 常量（qoj 无系列概念，只为满足层级约束） |
| 比赛 | `C` | `qoj:contest` | `qoj:4113` | 题目链接里的 `contest/<ID>` |
| 题目 | `P` | `qoj:4113` | `qoj:4113:20236` | `题目ID` 字段 |
| 提交 | `R` | `qoj:4113:20244` | `qoj:sub:2951241` | `提交ID` 字段 |

**两个刻意的选择：**

1. **题目用 `题目ID`（`20236`）而不是题号（`A`）**。
   题号是"比赛内位置"，改一次题面就可能变；`题目ID` 是平台分配的稳定主键。
   → 用题号当 key 会在某次变题号时**静默产生重复节点**。
2. **比赛省略 `<类型码>`**（`qoj:4113` 而非 `qoj:C:4113`）。
   比赛 ID 是纯数字、不可能与 `sub` 混淆，短一点更好读。
   代价是少了形式化防撞——由 **2.4 的全局唯一**约束兜底（重复会被检出）。

#### 其他平台（建议，待样本确认）

| 平台 | 平台码 | 比赛 | 题目 | 提交 |
|---|---|---|---|---|
| codeforces | `cf` | `cf:1920` | `cf:1920:A` | `cf:sub:123456789` |
| atcoder | `at` | `at:abc300` | `at:abc300:a` | `at:sub:12345678` |
| 洛谷 | `lg` | `lg:contest:1234` | `lg:P1001` | — |
| 牛客 | `nc` | `nc:12345` | `nc:12345:A` | `nc:sub:123` |

> **层级分隔符统一是 `:`**（`composeExtKey`：`${平台}:${比赛}:${题号}`，见 `src/features/AutoImport/extkey.js`）。
> CF 题号本身写成 `1920A`（连写），所以它的 extKey 是 `cf:1920:A`；
> 早先本文写过 `cf:1920.A`（点），**已按实现改回冒号** —— 契约以代码为准。
>
> 「层级前缀 = 父的 key + `:`」这条规则在所有平台上一致，便于 3.5 的自检。

#### 爬虫侧代码（示意）

```js
const P = 'qoj';
const sKey  = () => `${P}:contest`;                  // 比赛分组（满足 W→S→C 约束）
const cKey  = id => `${P}:${id}`;                    // 比赛  qoj:4113
const pKey  = (c, pid) => `${P}:${c}:${pid}`;        // 题目  qoj:4113:20236
const rKey  = sid => `${P}:sub:${sid}`;              // 提交  qoj:sub:2951241
```

**`qoj` 的 `contestId` 从哪来**（你的样本里没有这个字段）：

```
题目链接 = "https://qoj.ac/contest/4113/problem/20236"
                                   ↑ 4113 就是 contestId
```

一次正则（`/contest\/(\d+)/`）即可。**建议爬虫在题目记录里直接输出
一个 `contestId` 列**，比让应用去解析 URL 干净——
按 7.3 它会被 `fieldMap` 显式忽略，但它是 `extKey` 的来源。

### 3.5 应用侧一致性检查（只警告，不阻断）⚠️

应用不解析 `extKey`，只做**纯文本层面**的自检（4.8 的细化）：

| 检查 | 触发 | 粒度 |
|---|---|---|
| **格式可疑** | 首尾空白、含全角字符、长度 > 200、`extKey === 父extKey` | 逐条 |
| **前缀漂移** | 同一父下兄弟节点用了 ≥2 种前缀写法 | **按父聚合，只报一次** |

> **关于"层级串不起来"这条检查已被删除** —— 记录原因，避免日后被当成遗漏。
>
> 早期设计还要求「子 `extKey` 必须以 `父extKey + ":"` 开头」。
> 那个假设**从未成立**：本文档只要求 `extKey` 非空且全局唯一（3.1 / 2.4），
> **从不要求前缀嵌套**；而 3.4 的推荐拼法本身**就是扁平的**：
>
> ```
> qoj:4113        父 qoj:contest        ← 合法，却不以父为前缀
> qoj:sub:2951241 父 qoj:4113:20244     ← 合法，同样不以父为前缀
> ```
>
> 结果是它在**完全正确的数据上大量误报**（实现期实测确认）。
> 而"`父extKey` 写错"的真实兜底其实在**解析层**：父引用解析不到时，
> 应用会**直接拒绝该条**并报出父子双方的 key（2.3）——比字符串启发式准确得多。
> 既然准确性有保障，启发式只剩噪音，故删除。
>
> **教训**：推荐拼法（3.4）是**约定**，不是**约束**。任何"自检"都不能把
> 约定当成规则来校验，否则会把合法数据判成可疑。

> 再次强调：**这些只是提示，都不阻断导入。**
> key 规范由你负责，应用只负责告诉你它看到的不一致。

## 四、查重：能不错不漏

### 4.1 先明确一个取舍

「不错」与「不漏」在这个问题里**互相矛盾**，必须显式选一边：

| 错误类型 | 后果 | 可修复性 |
|---|---|---|
| **漏判**（该合并却新建） | 多一个重复节点 | ✅ 可修复（删掉重的那个） |
| **错判**（该新建却合并） | 覆盖真实数据 / 两个题被并成一个 | ❌ 不可修复 |

→ **原则：宁可漏判，不可错判。** 具体贯彻方式见决策 2：判定只用 key 精确相等，
相似度只用于事后警告。

### 4.2 判定规则：key 精确相等

**整条判定逻辑只有这一句：**

```js
// 作用域：已解析出的目标父容器内
matched = 该容器下的子节点中，存在 node.extKey === record.extKey
```

| 情况 | 行为 |
|---|---|
| 存在 `extKey` 精确相等的节点 | **合并**（进入逐字段策略，见第六节） |
| 不存在 | **新建** |
| 记录算不出 `extKey` | **拒绝该条**（见 4.4） |

**没有阶梯、没有降级、没有阈值、没有打分、没有启发式。**
`extKey` 是唯一的身份判定依据，且要求**逐字符完全一致**。

已删除的设计（曾考虑过，现已作废）：

| 已删除 | 删除理由 |
|---|---|
| L1 `platform:contestId:problemIndex` 独立层级 | 它已并入 `extKey` 的生成规则（见第三节），无需第二级 |
| L2 题号归一化匹配 | 题号是**展示槽位**不是身份；它是误合并的主要来源 |
| L3 标题模糊匹配 | 相似度永不参与判定（见 4.6） |
| `normalizeProblemId` 及其全部用途 | 只服务于已删除的 L2 |

### 4.3 唯一保留的硬规则：作用域隔离

**只在已解析出的父容器内查找。** 跨比赛、跨平台绝不匹配。

这条保留是因为它是**正确性**规则，与"是否模糊"无关：
`extKey` 只在**同一个父容器下**的兄弟节点之间有比较意义。
（注意与 2.4 的**全局唯一**约束不矛盾：全局唯一是"存储层不许重"，
作用域隔离是"匹配层不许跨容器认领"，两者各自成立。）

### 4.4 强制校验：无身份键即拒绝 ⛔

**导入的每条记录都要有身份键：`extKey`，或者（合成节点）`synthKey` —— 两个都空才拒绝。**
这是本功能的前置契约。合成节点**没有 `extKey`**（它的身份就是 `synthKey`，
见 `field-rules.md` §10 的合成键口径）⇒ "缺 extKey"不再一律拒绝。

| 记录状况 | 行为 |
|---|---|
| `extKey` 为非空字符串 | ✅ 使用（内容不解析） |
| `extKey` 缺失 / `null` / `trim` 后为空 | ⛔ **拒绝该条**，进 `errors`，不创建、不合并 |
| `父extKey` 在包内和树上都找不到 | ⛔ **拒绝该条**（见 2.3） |

**粒度**：**逐条拒绝**，不是整包报废。一条坏的记录不影响同一份 crate 里其它
记录的正常导入，但它必须出现在预览的错误计数里。

**错误信息必须可直接行动**——给出具体原因与可用信息，而不是"缺少身份键"这种废话：

```
✗ 第 37 条（题号 A "All Closed"）：父节点不存在
   父extKey = "qoj:4113"
   包内没有该 extKey 的记录，树上也没有该 extKey 的节点。
   处理：先导入比赛，或让爬虫在本包里补一条节点类型为 "C" 的记录。
```

> 这条契约的直接后果是：**存量节点必须先补 `extKey` 才能参与增量**。
> 配套功能见第八节。

### 4.5 收敛性保证

**第二次运行同一份 crate，必须一条记录都不改。** 这是可测的验收标准：

```
第一次导入 → 新增 N
第二次导入 → 新增 0、更新 0、跳过 N
```

配套手段就是第五节的内容指纹。

### 4.6 相似度警告：只提示，不判定 ⚠️

**硬约束：相似度永不参与任何判定，只参与提示。**

```
key 一致              → 合并（静默）
key 不一致 + 标题高度相似  → 新建 + ⚠️ 警告
key 不一致 + 标题不相似    → 新建（静默）
```

所以警告**不阻断、不门控、不做上限**。它是预览里的一列 + 一个计数，
作用是让你一眼看出**自己的 key 规范有没有破掉**。

> 定位澄清：这不是安全机制，是**体检指标**。警告过多说明 key 规范有问题，
> 不说明导入逻辑有问题。

**阈值**：

| 参数 | 默认 | 说明 |
|---|---|---|
| `DEFAULT_SIMILARITY_THRESHOLD` | `0.7` | 相似度低于它不吭声（常量在 `src/utils/similarity.js`）。越高警告越多 |
| 计算范围 | 仅同一父容器内 | 与 4.3 的作用域隔离一致 |

**相似度算法**（纯函数，可单测）：归一化标题后取两者较大值——

1. **Levenshtein 比率** —— 抓错别字、大小写、多余空格、版本后缀（`Two Sum` vs `Two Sums`）；
2. **token 集合相似度** —— 对符号与分隔符更鲁棒（`Div.1 + Div.2` vs `Div1+Div2`）。

> 已知局限（写出来是为了不让它被误当成 bug）：中文标题"同义不同译"
> （`Two Sum` vs `两数之和`）相似度会很低，**不会触发警告**。
> 这是算法能力的边界，不是配置问题。

**例外：**「不是同一件东西」的配对不报**（4.6 与 4.7 都适用；2026-10-03 扩充了一次）

**编号系列天然"高度相似"**：十场「2026…暑期联赛（1）…（10）」两两都是 0.96，
`Round 900` / `Round 901` 同理。这类配对没有任何信息量，报出来只是刷屏，
于是把这条检查真正要抓的东西（"同一道题被导成两个 key"）淹掉。

判据刻意很窄，**两类**（`similarity.js` 的 `differsOnlyByNumbers` + `plan.js` 的题号闸门）：

```
① 归一化后两者不相等，且**去掉数字「词」后剩下的词序列完全相同** → "只差序号"，跳过
② 同一个父容器里**题号不同**（`F` vs `F2`、`p:I` vs `p:J`）→ 一场比赛里题号不同就是两道题，跳过
```

用**词**而不是字符比较，是为了让"多一个序号"也归到同一类：
牛客 133885 的 B 题 `Slot Machine` 与 C 题 `Slot Machine 2` 是成对出现的续作，
key 各不相同，报出来同样只是刷屏。

⚠️ **② 是 2026-10-03 加的，起因是实测**：真包 3362 条 `intra-batch-duplicate` **全是这两类误报**
（3216 条同父不同题号 + 146 条不同父的同名题）。"题名逐字相同"也**不算**信号 ——
AtCoder 的重发题 `arc120 F` 与 `F2` 都叫 `Wine Thief`（合法）。
⇒ **真正的指纹只剩一个**：**同一个父里同一个题号出来两个 key**
（老 QOJ"题号全乱"那个 bug 的形态：字母重复 C,C,E,E,…）。这一条目前真包 **0 命中**，判据保留。

被跳过的**配对数**会记进 `summary.similaritySuppressed`，在预览摘要与 `crate:check` 里显示成
"已忽略 N 条'不是同一件东西'的相似标题"：**不报警 ≠ 悄悄丢**，你始终知道它跑过了
（实测真包：**3378 条警告 → 0**，其中 11566 条相似配对是被这条规则压掉的）。

> 实测效果（早期）：HDU 10 场（联赛 1…10）的 `crate:check` 警告从 **50 条降到 5 条**，
> 45 条是编号系列误报
> （`恋恋的序列` vs `恋恋的排列`、`phi master` vs `gcd master`），值得看一眼。
> 牛客 10 场（训练营 1…10，442 个节点）同理：**46 条被忽略、2 条保留** ——
> 保留的是 `Permutation Evaluation` / `Permutation Generation`（99.50 vs 71.56）
> 和 `Sequence（Median Version）` / `Sequence（Mex Version）`（0.20 vs 90.85），
> 差在**字母**而不是数字，正是这条检查该提醒的东西。

### 4.7 包内重复警告（intra-batch）⚠️

同一份 crate 内，两条记录 **key 不一致但标题高度相似** → 警告。

这基本总是**爬虫侧的 bug**：同一道题被导出了两次，但两次的 key 不一致。

**必须在应用之前检测**，因为不检测的后果是静默的：逐条按顺序应用时，
后一条会以"新建"的身份落到容器里，两条内容若不完全相同则指纹不同，
于是它们**互相覆盖、悄悄合并成一个**——你看到 `新增 2`，实际得到 1 个节点。

**优先级高于与已有节点的比对**：包内自相矛盾比与树上不一致更值得先看。

同样遵守上面的「只差序号」例外（否则十场同名联赛会刷出 45 条）。
注意**比对范围是全类型的**（不像 4.6 只比 P），所以比赛、系列这类容器的
名字也在比对之列 —— 编号系列的误报主要就来自这里。

但**只比同类型**（决策 24）：`XCPC`(W) 与它下属的 `ICPC`(S) 相似度 0.75，
跨类型比纯属噪声 —— 一个是平台、一个是系列，不可能是"同一道题两个 key"。
（这条是 XCPC 导入时实测踩出来的：`crate:check` 报了一条
`xcpc` vs `xcpc:s:icpc` 的"包内高度相似"。）

### 4.8 key 规范一致性警告 ⚠️

既然 key 规范由用户负责，就要能**看见自己的规范破了没有**。两条纯检测警告：

| 检查 | 触发 | 粒度 |
|---|---|---|
| **格式可疑** | 首尾空白、全角字符、长度 > 200、`extKey === 父extKey` | 逐条 |
| **前缀漂移** | 同一个 `父extKey` 下的兄弟节点用了 ≥2 种前缀写法<br>（如 `qoj:4113:20236` 与 `qoj:prob:20237` 混用） | 按父聚合，**只报一次** |

同样**只警告、不阻断、不自动修正**。自动"修正"key 会直接破坏幂等
（改了 key 就等于换了身份），所以这个功能**刻意不做**。

> **为什么"层级串不起来"不在表里**：那条检查假设了前缀嵌套约定，
> 而本设计从不要求它——详见 **3.5** 的删除说明。凡把"推荐拼法"
> 当规则来校验的自检，都会在合法数据上误报。

> **只按父聚合报一次**，不逐条刷屏：一次导入几千条时，逐条报同一种
> 规范漂移会把真正的问题淹掉。用户要的是"知道规范破了"，不是"看 N 遍"。

## 五、指纹与幂等

每条记录带内容指纹：

```json
"fingerprint": "fnv1a:1a2b3c4d"
```

**算法**（应用侧可自行计算，爬虫也可预计算）：

1. 取 `extKey` / `type` / `fields` / **`clue`（元列 `账户线索`）** 四项
   （**哈希的是这四个**，见 `src/features/AutoImport/contentHash.js` 的 `hashRecord`）；
2. 按键名**字典序**排序（递归）后序列化为紧凑 JSON（无空格）；
3. 算 **FNV-1a 32 位**（`hashString`，**不用 crypto**：它要在浏览器里同步跑、且只需够用的碰撞率），
   取 8 位小写十六进制；
4. 前缀 `fnv1a:`。

**关键**：指纹**只覆盖内容，不覆盖** `generatedAt`、`source`、`crateVersion`、`分类依据`、`链接分类`。
这样"同一道题、同一份内容"无论出现在哪个包、什么时间生成，指纹都相同。

> **为什么 `账户线索` 算内容**（它也是元列）：它会写进**来源层**（每条值的 `account` / `clue`）——
> 线索变了就是树里的数据要变。不算进来的后果实测过：`nk` / `hdu` 声明 handle 之后重导一次，
> 业务字段一个字没变 ⇒ 整批判"跳过"、预览写着「更新 0」，而界面上那些提交其实刚从
> "客观值"变成"归到某人名下"。**带线索的记录即使没有可写字段变化，也算更新**（见 `plan.js`）。

| 记录状态 | 行为 |
|---|---|
| 匹配到节点，且 `node.importFingerprint === record.fingerprint` | **整条跳过**（no-op，不算更新） |
| 匹配到节点，指纹不同 | 进入逐字段合并，执行后写回新指纹 |
| 未匹配到节点 | 新建，写入指纹 |

`node.importFingerprint` 同样是插件字段（migration 补齐，默认 `''`）。

## 六、属性合并策略（保护手填数据）

匹配到目标后，**逐字段**按策略写入。

### 6.1 四种策略

| 策略 | 语义 |
|---|---|
| `never` | 永不覆盖（缺省视为该字段不存在于本次导入） |
| `fill-if-empty` | 仅当当前值为空（`''` / `0` / `'-'` / 空数组）才填 |
| `overwrite-if-changed` | 值不同就覆盖 |
| `force` | 无条件覆盖 |

### 6.2 默认策略表

**表的索引是「内部字段名」**——即 `fieldMap`（7.3）映射之后的名字。
爬虫用什么列名不影响本表。

> **`link` 为什么是 `fill-if-empty` 而不是 `never`**（2026-09 修订）：
> 早期把它划进"绝不写"，想保护"你换过的链接"。但 `fill-if-empty` 同样保护
> —— 非空一律不动 —— 而**空着的时候还能补上**。
> 现实场景：爬虫早期不给比赛节点写链接，之后开始写了；
> 若策略是 `never`，那些已经导入的比赛节点**永远补不上**，
> 只能逐个手贴或删了重导。`fill-if-empty` 让重导一次即可补齐。
> 唯一的行为差别：**你主动清空的链接会被再次填上**。
> 若你确实需要"清空后保持为空"，把 `constants.js` 的
> `EXISTING_NEVER`（现在是 `['tags','synthKey','time','status']`）**加上 `link`** 即可回到"永不覆盖"。
> ⚠️ 别再找 `EXISTING_POLICY_DEFAULTS` 里 `link` 那一行：那张已存在策略表是**派生**的
> （`buildPolicyTable('existing')`：默认 `fill-if-empty`，例外只有 `EXISTING_OVERWRITE` / `EXISTING_NEVER` 两组），
> 里面没有逐字段的 `link` 行。

#### P（题目）

| 内部字段 | 已存在节点 | 新建节点 | 理由 |
|---|---|---|---|
| `name` | `fill-if-empty` | `overwrite-if-changed` | 你可能改过题名，别冲掉 |
| `problemId` | `fill-if-empty` | `overwrite-if-changed` | 同上 |
| `cfDifficulty` | `fill-if-empty` | `overwrite-if-changed` | CF 分数会随 rating 漂移，但手填优先 |
| `ratio` | `fill-if-empty` | `overwrite-if-changed` | 通过率会漂移 |
| `link` | `fill-if-empty` | `overwrite-if-changed` | 空才补；你换过的链接不会被冲 |
| `tags` | `never` | `overwrite-if-changed` | 标签是你手工整理的知识点，最忌被冲 |
| `remark` | `never` | `never` | **题解，唯一不可再生数据，永不由导入写** |
| `status1` | ❌ 不可写 | ❌ 不可写 | 由核心 `autoCompute` / 用户选择决定 |
| `status2` | ❌ 不可写 | ❌ 不可写 | 由 R 子节点推导（见 7.6）。**v8.1 起判据里多了 R 的 `submitKind`**：范围内有一发 `赛时` 的 AC ⇒ `4 赛时通过`，否则 `3 赛后补题` |
| `acTime` / `lastSubmitTime` | ❌ 不可写 | ❌ 不可写 | 由 R 子节点推导 |
| `xcpcDifficulty` | ❌ 不可写 | ❌ 不可写 | 由 `ratio` 派生（`getXcpcDifficulty`） |

> **派生字段由谁算**：`status1` / `status2`、`acTime` / `lastSubmitTime`、
> `xcpcDifficulty`、`statusComplete1` / `statusComplete2` 全部由
> `core/autoCompute.js` 的 `TYPE_AUTO_PROPS` 在**每次事务末尾**统一重算
> （`fullAutoUpdate`）。导入只写"原料"（`ratio`、R 子节点），
> **不写推导结果**——这正是"导入拒绝写这些字段"能成立的前提。
>
> 踩过的坑：`xcpcDifficulty` 一度只在 `core/ops/node.js` 的 `updateP`
> （手动编辑题目）里算，于是**导入进来的题目**永远停在默认值 `'-'`，
> 树上显示成 `28.19%(-)`——明明有通过率，却报"未填写难度"。
> 现已补进 `TYPE_AUTO_PROPS.P`，手动改 / 导入 / 旧批量导入三条路径同源。
>
> 推论：**如果你在树上看到某个派生字段不对，先看 `TYPE_AUTO_PROPS` 里有没有它**，
> 而不是去改导入器。派生字段的正确性只能由派生引擎负责。

#### C / W / S（容器）

| 内部字段 | 已存在节点 | 新建节点 | 理由 |
|---|---|---|---|
| `name` | `fill-if-empty` | `overwrite-if-changed` | 容器靠 `extKey` 认，不靠名字，所以名字可以安全更新 |
| `contestTime` | `fill-if-empty` | `overwrite-if-changed` | |
| `link` | `fill-if-empty` | `overwrite-if-changed` | 比赛/平台链接；空才补（见 6.2 的说明） |
| `statusComplete1` / `statusComplete2` | ❌ 不可写 | ❌ 不可写 | 由子节点推导 |

#### R（提交记录）

R 的身份是 `提交ID`，**一条记录只对应一个 R，永远不会发生"合并"**：

| 内部字段 | 策略 | 理由 |
|---|---|---|
| `time` | `overwrite-if-changed` | 同一提交的时间不会变；能变说明爬虫修正过 |
| `status` | `overwrite-if-changed` | 判题结果可能从 `PD` 变 `AC`，**应该更新** |
| `link` | `fill-if-empty` | 同一提交的链接恒定；空着才补，非空不动 |
| `submitKind` | `fill-if-empty` | 提交性质（赛时/VP/补题）。**空值是重要信息**（= 判不出），所以只补空 —— 判出来的值不会被后来的"判不出"盖掉 |
| `language` / `timeUsed` / `memoryUsed` / `codeLength` | `fill-if-empty` | 运行信息；客观测得值，只补空 |

> 注意 R 的 `status` 用 `overwrite-if-changed` 是**刻意的**：
> 一场比赛期间爬虫可能先抓到"提交中"，稍后抓到"AC"。
> 这条路径是让提交结果保持最新的唯一手段，
> 也是 P 的 `status2` 能自动变准的前提（7.6）。
>
> 关于 `link` 的两轮修订（留着是因为"为什么不是别的值"比"是什么值"更容易踩）：
> 最早写成 `overwrite-if-changed`（与实现不一致）；
> 后来改成 `never`，理由是"已存在节点的 `link` 不覆盖"这条通用规则；
> **2026-09 又统一改成 `fill-if-empty`** —— 见 6.2 的说明：
> `fill-if-empty` 既保住了"不覆盖你换过的链接"，又能补上空链接。

导入包可通过 `defaults.fieldPolicies` 覆盖上表，但**所有 ❌ 行不可被覆盖**。

### 6.3 写空值的禁令

字段在本次记录里**缺失** ≡ 不改该字段。

**绝不允许**「记录里没有该字段 → 把节点上该字段清空」。
这条是防止爬虫数据缺列时批量抹掉你的数据。

## 七、导入包格式（crate）——给爬虫的契约

### 7.1 完整示例

```json
{
  "crateVersion": 1,
  "source": { "id": "qoj-scraper", "label": "QOJ 爬虫" },
  "generatedAt": "2026-09-13T22:06:07Z",

  "fieldMap": {
    "题号": "problemId",
    "题目名称": "name",
    "比赛名称": "name",
    "比赛时间": "contestTime",
    "题目链接": "link",
    "提交链接": "link",
    "结果": "status",
    "提交时间": "time",

    "题目ID": null,
    "contestId": null,
    "提交ID": null
  },

  "defaults": {
    "fieldPolicies": { "cfDifficulty": "overwrite-if-changed" }
  },

  "records": [
    {
      "节点类型": "W",
      "extKey": "qoj"
    },
    {
      "节点类型": "S",
      "extKey": "qoj:contest",
      "父extKey": "qoj",
      "比赛名称": "QOJ Contest"
    },
    {
      "节点类型": "C",
      "extKey": "qoj:4113",
      "父extKey": "qoj:contest",
      "比赛名称": "2026 Multi-University Training Contest 1",
      "比赛时间": "2026-09-13 12:00"
    },
    {
      "节点类型": "P",
      "extKey": "qoj:4113:20236",
      "父extKey": "qoj:4113",
      "题号": "A",
      "题目名称": "All Closed",
      "题目ID": "20236",
      "contestId": "4113",
      "题目链接": "https://qoj.ac/contest/4113/problem/20236",
      "是否通过": false
    },
    {
      "节点类型": "R",
      "extKey": "qoj:sub:2951241",
      "父extKey": "qoj:4113:20244",
      "提交ID": "2951241",
      "提交链接": "https://qoj.ac/submission/2951241",
      "结果": "AC",
      "提交时间": "2026-09-13 22:06:07",
      "得分": "100.000000",
      "时间": "63ms",
      "内存": "40416kb",
      "代码长度": "3.2kb"
    }
  ]
}
```

**五个要点：**

1. **平台记录（`W`）省略 `父extKey`** → 挂在根下（3.3）；
2. **`S` 层不可省**：`W` 下不能直接放 `C`（见 **2.5**），
   所以 qoj 这类没有"系列"概念的平台必须在中间插一个 `S` 容器；
3. **C / P / R 混在同一个 `records` 数组里**——它们只是 `节点类型` 不同的记录，
   拓扑排序（2.2）会把它们排成 W → S → C → P → R，不需要分文件、不需要特殊处理。
   （上例中 `R` 的父 `qoj:4113:20244` 就是样本里 I 题的 `题目ID`。）
4. **`题目ID` 与 `contestId` 映射为 `null`** = 显式忽略，
   它们**不进节点字段**，只是爬虫在拼 `extKey` 时的中间量（3.4）；
5. **`是否通过` 完全不出现在 `fieldMap` 里** = 未使用字段，
   会被记进导入记录后丢弃——它本来就该由 R 推导（7.6）。

### 7.2 包级字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `crateVersion` | ✅ | 当前 `1`。版本不符 → **整包**报错，不猜 |
| `source.id` | ✅ | 来源标识，用于导入记录 |
| `source.label` | ❌ | 显示名 |
| `generatedAt` | ❌ | 仅供显示，**不进指纹** |
| `fieldMap` | ✅ | 见 7.3 |
| `defaults.fieldPolicies` | ❌ | 覆盖 6.2 的默认表（❌ 行除外） |
| `records[]` | ✅ | 非空 |

### 7.3 `fieldMap`：爬虫列名 → 内部字段 ⭐

**这是"字段由爬虫命名、应用却能套用策略"的那座桥。**

```json
"fieldMap": {
  "题号": "problemId",
  "题目名称": "name",
  "题目ID": null,
  "题目链接": "link"
}
```

| 值 | 含义 |
|---|---|
| `"<内部字段名>"` | 该列映射到内部字段，**参与 6.2 的策略判定** |
| `null` | **该列被显式忽略**（同时解除 7.3 / 决策 14 的"未使用字段"记录，见下） |
| 列名未出现在 `fieldMap` 中 | 视为**未使用字段** |

**语义要点：**

1. `fieldMap` 是**包内的**，写一次、永久生效——**不会弹窗让你手工配**。
   （这正是它相对现有批量导入的映射对话框的改进：配置随数据走，不随会话走。）
2. 映射后键名统一为**内部字段名**，6.2 的策略表照常按内部名索引。
3. `题号`/`题目名称` 这类"看起来像"的列**不会自动被采纳**——
   必须显式列在 `fieldMap` 里，否则按未使用处理。

**未使用字段的记录**（决策 4）：包里出现过、但 `fieldMap` 未映射的列名，
记进**导入记录**（只存**字段名**，不存值），出现在「导入记录」里：

```
2026-09-13 22:10  qoj-scraper  新增 14 / 更新 0 / 跳过 0
  未使用字段：得分, 时间, 内存, 代码长度
```

这样将来你想把「内存」也存起来时，**知道爬虫早就在给这个字段了**，
不必重新翻爬虫代码。

### 7.4 记录级字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `节点类型` | ✅ | `O`/`W`/`S`/`C`/`P`/`R` |
| `extKey` | ✅ | 非空字符串；缺失或空 → **逐条拒绝**（4.4） |
| `父extKey` | ❌ | 留空即挂根（3.3）；非空时包内或树上必须有对应节点，否则**逐条拒绝**（2.3） |
| （其余键） | ✅ | 由 `fieldMap` 决定哪些进内部字段、哪些被忽略 |

**明确不需要的字段**：不再有 `path`、不再有 `ext` 子对象、不再有 `fingerprint`
（指纹由应用按 5 的算法自行计算，爬虫不必实现）。

### 7.4.1 `账户线索`：这条记录是**谁**的 ⭐（v8.1）

爬虫要**如实搬运**、但**不做判断**的一个元列。写法与记录字段并列：

```jsonc
{ "节点类型": "R", "extKey": "qoj:sub:2951241", "父extKey": "…",
  "结果": "AC",
  "账户线索": { "source": "qoj", "field": "提交者", "value": "someone" } }
```

| 键 | 含义 |
|---|---|
| `source` | 平台/来源 id（`qoj` / `pta` / `cf` / 榜单来源…） |
| `field` | 用**哪一列**认出人（`提交者` / `队伍` / `handle`…） |
| `value` | 那一列的值 |

应用侧的行为：拿 `{source, field, value}` 去查**用户在账户界面里维护的映射**
（如 `qoj : 提交者 = someone`）→ 认得出就把这条值的 `account` 记成该账户；
**认不出就当客观值**（`account` 空），并在导入摘要里报"没认出来 N 条"。

**为什么必须搬运它**：不搬的话，这条提交在应用里就是"客观数据"——
于是"只看我的"看不到它、"各自补题情况"（多账户对比）里也不会出现在任何人那一列。
**它不改变任何字段值，只决定这条值算谁说的。**

各平台的常用线索（本项目现有爬虫）：

| 平台 | 线索 | 值从哪来 |
|---|---|---|
| QOJ | `{source:'qoj', field:'提交者', value:<提交者>}` | 提交页面的"提交者"列 |
| PTA | `{source:'pta', field:'队伍', value:<队名>}` | 提交响应里的 `teamInfo.teamName`（榜单里**没有**"提交者"列，队名是唯一能认出"是谁"的东西） |
| Codeforces | `{source:'cf', field:'handle', value:<handle>}` | 提交里的 `author.members[]`（本项目 XCPC 的 handle 来自 `acm-data/raw/Scaper/me.json` 的 `cf.handle`，由生成器写进清单 `defaults.cfHandle`） |

> 没有"提交者"这类列、而且这份数据只可能是某个人的（例如"我自己账号的提交列表"）时，
> 也可以把线索写成 `{source:'qoj', field:'本人', value:'是'}` 之类的约定 ——
> 只要能对上用户维护的那条映射即可。**关键是别让 R 变成无主的客观值。**

#### 线索必须**唯一确定**一个账户（重名怎么办）

匹配规则是 **`(source, field, value)` 三元组全等**（`core/accounts.js` 的 `resolveAccount`）：
两条映射声明同一个三元组 → 判成**冲突，谁都不认领**。

所以爬虫要留神这类"会重用的标识"：

| 会重用的标识 | 例子 | 做法 |
|---|---|---|
| **队伍名** | `TEAM0` 每届都用、队友换了三批 | **把赛季放进 `source`**：`{source:'pta:icpc2026', field:'队伍', value:'TEAM0'}`（应用里每届建一个账户） |
| 昵称 / handle | 同一人换号，或不同人重名 | 同上去加"平台/赛季"维度，或改用平台的**稳定 id**（`field:'用户id'`） |
| 学校 / 组织 | 只能定位到学校 | 别拿它当线索（会大面积冲突） |

**原则**：`value` 尽量原样搬运（便于和原始数据核对），**区分维度放进 `source`**
（或 `field`）。`source` 本来就是"来源命名空间"，这样写读起来也顺。
本项目 XCPC 的做法是 `pta:<mid>`（赛季层，`mid` 就是清单里的年份/省份层）。

### 7.4.2 `链接分类`：链接按**用途**记账 ⭐（v8.2）

与 `账户线索` 一样是**记录级元列**（`C` 用来记比赛入口，v8.3 起 `W`/`S` 也用它记**源站上的容器页**），
写法与记录字段并列：

```jsonc
{ "节点类型": "C", "extKey": "aux-xcpcio:c:icpc2025chengdu", "父extKey": "…",
  "name": "…",
  "链接分类": {
    "board":    [{ "v": "https://board.xcpcio.com/icpc/50th/chengdu", "src": "xcpcio-icpc2025chengdu" }],
    "problems": [{ "v": "https://qoj.ac/contest/2567", "src": "qoj-icpc2025chengdu" }],
    "repo":     [{ "v": "https://github.com/…icpc2025chengdu.srk.json", "src": "rankland-index-…" }]
  } }
```

**为什么要它（两条原则）**：

1. **"数据爬取部分不应该有『存在多值时排除一些值』的逻辑"** —— 所以同一个类别有**几条就列几条**，
   爬虫**不选、不排序、不丢弃**；以前"谁占 `link`"靠来源数组顺序，是偶然，不是语义。
2. 取舍放在**应用层一处**（`src/features/AutoImport/plan.js`）：
   `link` = 第一条 `problems`（**补题链接**，没有就空着，不拿别的类别凑）；
   缓存值 `link` 按类别优先级取第一条（**补题 → 榜单 → 仓库 → 其它**），其余候选全部留在来源层。

| 类别 | 含义 | 例 |
|---|---|---|
| `board` | 榜单（能看到排名的那页） | `pintia.cn/rankings/…`、`board.xcpcio.com/…`、牛客比赛页 |
| `problems` | 补题入口（题面/重现赛） | `qoj.ac/contest/…`、`codeforces.com/gym/…`、`vjudge.net/contest/…`、题面 PDF |
| `repo` | 仓库/数据文件（**不是给人点的入口，但也不丢**） | `github.com/algoux/srk-collection-raw/…` |
| `browse` | **源站上的容器页**（v8.3 起；W/S 节点用） | `qoj.ac/`（平台）、`qoj.ac/category/<id>`（QOJ 分类）、`codeforces.com/gyms`（CF gym 列表） |
| `unknown` | 认不出的 | `ccpc.io/`、`acm.hdu.edu.cn/search.php?…` |

- **类别由产出它的适配器声明**（它手上有 `title` 等上下文）；`crate.classify_link()` 只按 URL 兜底
  —— 牛客比赛页就是"既是榜单又是题面"的例子，光看 URL 分不出来。
- **没有对应类别的链接也需要落点**：它们会进 `其它来源值`（带 `linkKind`），再写进**来源层**，
  树上按类别分组显示（**「仓库」与「未知」非空也显示**）。所以"一个字段只能装一个值"不再是丢值的理由。
- 应用侧读的是**值的类别**（来源层每条值上多了个可选 `linkKind`），别再自己按 URL 猜。

### 7.5 R（提交记录）的字段映射

R 节点的字段：`time` / `status` / `link` + **v8.1「先提取备用」的四个运行信息**
（`language` / `timeUsed` / `memoryUsed` / `codeLength`，口径统一成 **毫秒 / 字节**）：

| qoj 列 | 内部字段 | 转换 |
|---|---|---|
| `结果`（`AC` / `WA` / `TLE`） | R.`status` | 与 `A_constants.js` 的 `STATUS_OPTIONS` **完全对齐**，直通 |
| `提交时间` | R.`time` | `normalizeTime("2026-09-13 22:06:07")` → `2026.09.13 22:06` |
| `提交链接` | R.`link` | 直通 |
| `提交ID` | → **R 的 `extKey`**（`qoj:sub:2951241`，按 3.4） | 不进字段，进身份；`fieldMap` 里映射为 `null` |
| （爬虫自己判的） | R.`submitKind` | 提交**性质**：`赛时` / `VP` / `补题`。**判不出就留空**（不写"未知"）：留空才能被下次抓取补上。它决定父题目 `status2` 是「4 赛时通过」还是「3 赛后补题」（见 6.2 的 P 表） |
| `使用语言` | R.`language` | 直通（**只有全局列表页 `/submissions?submitter=` 有这一列**；场次页没有 → 写 `None`） |
| `时间` | R.`timeUsed` | `95ms` / `1.2s` → **毫秒**（与 CF 的 `timeConsumedMillis` 同口径） |
| `内存` | R.`memoryUsed` | `4956kb` → **字节**（×1024；与 CF 的 `memoryConsumedBytes` 同口径） |
| `代码长度` | R.`codeLength` | `2.0kb` → **字节** |
| `得分` | ❌ 无对应 | 按决策 14 记录字段名后丢弃（不要 ICPC 式计分） |

> **时间格式无需特殊处理**：`normalizeTime` 的数字路径接受 14 位
> （`20260913220607`），输出 `2026.09.13 22:06`，与 `getNowStr` / `formatTime`
> 的格式一致，因此 `computePacTime` 的字符串排序比较照常工作。
> **秒会被丢弃**——同一分钟内多次提交时间相同，这是可接受的（现状如此）。

### 7.6 爬虫完全不必管状态 ⭐

看 `qoj_problems.json` 里的 `是否通过: false`——**爬虫不需要写它，应用也不要读它**。

原因：P 的 `status2` / `acTime` / `lastSubmitTime` 由 **R 子节点**
经 `computePstatus2` / `computePacTime` 自动推导
（见 `core/autoComputeRules.js`）。

**含义**：爬虫只要老老实实把 **R（提交记录）** 导进来，
题目通过状态就**自动**正确了。这是 6.2 里那三个 ❌ 字段的现实意义——
它们不是"暂时不许写"，而是"根本不必写"。

### 7.7 解析器的宽容度

`parseCrate` 内置少量**平台适配器**，把平台原生导出直接转成 crate——

**但仅用于适配结构差异**（顶层是数组还是对象、有没有 `fieldMap`、`extKey` 怎么拼），
**不用于猜测字段语义**：字段语义一律由包内 `fieldMap` 显式声明。

| 适配器 | 输入形态 | `extKey` 生成建议 |
|---|---|---|
| `qoj` | 顶层数组，中文列名（现有两个样本文件） | 题目 `qoj:<contestId>:<题目ID>`、比赛 `qoj:<contestId>`、提交 `qoj:sub:<提交ID>` |
| `codeforces` | `{ problems: [{ contestId, index, name, rating, tags }] }` | `codeforces:<contestId>:<index>`（⏸ **未实现**：只在 `constants.js` 的 `ADAPTERS` 里登记了名字，没有实现文件） |
| `atcoder` | 待补样本 | ⏸ 暂搁置（手头没有样本可测；有样本再说，不算待办） |
| `luogu` | 待补样本 | ⏸ 暂搁置（手头没有样本可测；有样本再说，不算待办） |
| `nowcoder` | 待补样本 | ⏸ 暂搁置（手头没有样本可测；有样本再说，不算待办） |

适配器是纯函数，可单测。

## 八、补身份键（存量数据接入）

**这个功能是必需的，不是可选的。** 因为 4.4 强制要求 `extKey`，
而你**现有节点一个 `extKey` 都没有**——不补，首次导入就是把整棵树当重复数据全新建一遍。

### 8.1 先认清一个不对称

| 节点类型 | `extKey` 从哪来 |
|---|---|
| **P（题目）** | 爬虫给（`codeforces:1920:A`）——你不可能手猜 |
| **W / S / C（容器）** | **由爬虫决定并写在 `父extKey` 引用链上**——不是你决定 |

所以：**补 key 的本质是「把爬虫用的 key 告诉你，让你挂到已有节点上」**，
而不是"让你发明一个 key"。这个认识决定了下面三个入口的形态。

### 8.2 入口 A：从「父节点解析失败」现场一键补（主入口）

导入时若某条记录的 `父extKey` 解析不到父节点，错误信息**直接带上爬虫用的 key**：

```
✗ 第 1 条（节点类型 P "All Closed 题号A"）：父节点不存在
   父extKey = "qoj:4113"
   包内没有该 extKey 的记录，树上也没有该 extKey 的节点。
   [为此创建一个比赛节点]   [挂到已有节点…]   [忽略此条]
```

选「挂到已有节点」→ 列出当前层级已有节点让你点 → 走事务补写 `extKey`
→ **原地重试这次导入**。

**这是主入口**，因为它让补 key 发生在**你正好知道该挂哪儿**的时刻
（而不是事后回忆"我那个 QOJ 比赛节点该叫什么 key"）。

### 8.3 入口 B：`🔑 补身份键` 页（存量清理）

文件夹视图加一页 `🔑 补身份键`，分两块：

**① 顶部：当前文件夹**自身**的 extKey**

这一块是为**根节点**而设的：根不是任何节点的子节点，
不会出现在下面的子节点列表里，没有这块表单就永远够不着它。
在根文件夹打开本页 → 设置的就是根节点的 key。

**② 下方：当前文件夹的子节点列表**

| 列 | 内容 |
|---|---|
| 节点 | 名称 / 类型 / 题号 / 当前 `extKey`（空则标红） |
| 建议键 | 能从名称+题号推出候选时，提供**一键填充** |
| 操作 | 「更换」按钮（见 8.6） |

支持**整页粘贴对照表**——键与**题号**配对：

```
qoj:4113:20236    A
qoj:4113:20237    B
qoj:4113:20238    C
```

**用题号/名称配对，不用顺序配对。** 顺序配对在数据缺行时会**错位**，
而错位写入的 key 是静默的、不会被发现的——这是本节最重要的一条设计约束。
（上表若被顺序配对，第 2 行就会把 `qoj:4113:20237` 写到 C 题上。）

### 8.4 入口 C：按规则批量生成（逃生舱）

格式 `<前缀>:<序号>`，如 `local:1`、`local:2`。

**明确定位为逃生舱，界面上要直白标注**：生成的 key 爬虫**永远不会用**，
所以这批节点**永远无法与爬虫对账**。它只解决"让校验通过"，不解决"能和爬虫增量"。

### 8.5 四条配套约束

1. **必须走 `execute()`**：单次事务、可撤销。
2. **重复执行幂等**：不覆盖已有 `extKey`，只补空的。
3. **冲突拒绝**：目标父层级下已存在同 `extKey` 的节点 → **不自动挑一个**，
   报错让你决定。自动挑 = 静默合并两个节点，不可修。
4. **补完跑一次 `autoUpdateSubtree`**：`extKey` 本身不参与派生计算，
   但补的是容器 key 时会改变容器的归属语义，统一重算更省心。

### 8.6 更换 / 清空 key（危险操作的显式通道）

上面 8.5 只允许"补空的"——那是**默认安全语义**。但由此产生一个死角：

> **补错了 key 怎么办？** 若永远不能改，那个错误会一直留着，
> 而副作用是「以后每次导入都多一个重复节点」——正是最该避免的情况。

所以提供一个**显式的「更换」入口**（`🔑 补身份键` 页每行的「更换」按钮）：

| 操作 | 语义 |
|---|---|
| **更换** | 写入新 key；旧 key 从索引移除 |
| **清空** | 输入留空并确认 → 退回"未设身份"，之后可重新补 |

**为什么必须由人显式操作，而不能让导入流程自动做**：

改了 key 就等于**换了身份**。爬虫那边**仍然用旧 key**，
于是**同一份导入包的下一次导入会新建一个节点**。
旧节点上的题解不会丢，但会与爬虫数据**脱钩（两边分叉）**。

因此 UI 有三道闸：

1. 表单里**先写清后果**（不是藏在 tooltip 里）；
2. 点确认时**再弹一次 `window.confirm`**，复述后果并说明可撤销；
3. 走 `execute()` 事务，**Ctrl+Z 可回退**。

**仍然保留的保护**：目标 key 已被**别的**节点占用 → 照旧拒绝。
那是脏数据，不能靠"覆盖"来掩盖。

对应实现：

- `core/ops/upsert.js` 的 `assignExtKey(..., { allowOverwrite })`
  —— 默认 `false`（只补空的），`true` 才允许更换/清空
- `features/AutoImport/apply.js` 的 `changeExtKeyAssignments()`
- `features/AutoImport/extKeyPanel.js` 的「更换」按钮

## 九、冲突、警告与预览

### 9.1 不阻断执行的状态

| 状态 | 触发 | 预览里的表现 |
|---|---|---|
| **警告** | 4.6 相似度（`similar-title` / `similar-key-conflict`）/ 4.7 包内重复（`intra-batch-duplicate`）/ 4.8 规范不一致（`key-*`）/ 策略覆盖（`policy-*`）/ 树上已有重复 `extKey`（`tree-extkey-conflict`） | ⚠️ 仅提示，**照常执行** |
| **计数**（不是状态） | 新增 / 更新 / 跳过（指纹没变、或合并后没有字段要写 ⇒ 跳过；**两个例外**：① 带 `账户线索` 的记录 —— 线索要写进来源层；② 要**换父**的记录 —— 位置是效果的一部分，见 `plan.js`）+ **🔀 重挂**（换父有几条） | 预览顶部那几个数 |

**只有这几档**：**没有"提示"档，也没有"待确认"档**——
容器不存在时**不隐式创建**（2.3），所以不存在"容器将被创建"这种条目；
"待确认"随 4.4 的守卫一起被删除 ——
既然无 key 直接拒绝、key 一致直接合并，就不存在需要用户逐条裁决的中间态。

### 9.2 硬错误（该条不执行）

| 错误 | 例子 | 粒度 |
|---|---|---|
| 身份错误 | 算不出 `extKey`（4.4） | **逐条** |
| 寻址错误 | 父节点解析不到（2.3）、`父extKey` 成环、父类型不允许该子类型 | **逐条** |
| 身份错误 | `extKey` 缺失/为空（4.4）、包内 `extKey` 重复（3.2） | **逐条** |
| 结构错误 | `crateVersion` 不符、`records` 为空、JSON 解析失败 | **整包** |

**粒度区分是刻意的**：一条坏记录不该拖累同包里其它 999 条；
但包本身格式就不对时，没有"部分成功"可言。

### 9.3 事务语义

- **预览阶段只读**，不改任何状态（dry-run）；
- **执行阶段一次 `execute()` 事务**——要么全成，要么全回滚
  （`transaction/executor.js` 的校验失败即回滚）。
- ⚠️ **"回滚"覆盖的是事务本身，不包括落盘**（v8.4）：落盘改成**合并延迟写**之后，
  写盘失败**不再**回滚这次事务，而是表现为"保持未保存 + 自动重试 + `console.error`"。
  导入这种"一次写很多"的操作因此**不会因为磁盘抖动白干**，
  但也意味着"崩溃最多丢最后 ~300ms 的改动"。

> 粒度是"逐条跳过"而非"整包回滚"：被拒绝的记录在**进事务之前**就已剔除，
> 因此事务内不会因它们失败。

### 9.4 导入**不**展开节点（默认全折叠）

新建节点后**不**把父节点设成 `expanded = true`（`core/ops/upsert.js`）。
一次导入动辄上百个节点，逐级展开会把整棵树炸开，还会撞上
`settings.performance.expandedNodeBlockLimit` 的渲染上限
（`core/validate/expanded.js`）。

这会带来一个副作用：导入完可能"看不到东西"（都折叠着）。这是刻意的——
想找新节点用**定位**动作（`EVENTS.REVEAL_NODE` → `ui/revealNode.js`
会按需展开那条链），或点「折叠全部 / 展开」自行浏览。

> 应用里其它"手动加一个子节点"的路径（`core/ops/tree.js`、`core/ops/batch.js`）
> 仍然会展开父节点——那是**单点操作**，展开是帮忙。
> 批量导入是另一回事，所以这里刻意与之不同。

## 十、界面

新增一级 Tab：`📥 节点自动导入`（`api.registerTab`，`order: 1400`，排在
`主视图 → 数据统计` 之后、`🧩 判重整理`（`data-order="1500"`）之前）。
另外在文件夹模式的节点视图加两页（`api.registerFolderView`）：

- `📥 导入/同步` —— 把**当前文件夹节点**作为默认父容器（记录仍以 `父extKey` 为准）；
- `🔑 补身份键` —— 见 8.3。

### 10.0 两个「导入」入口什么关系（v8.4 写清）

**同一个插件、同一套预览与执行**（都走 `loadFiles` → `renderPanel` → `onExecute` → `execute`，
都进历史/快照），**差别只有两点**：

| | 全局「📥 节点自动导入」（`registerTab`） | 节点下「📥 导入/同步」（`registerFolderView`） |
|---|---|---|
| 挂在哪 | 顶部 `#tab-bar` 的插件 tab | 文件夹节点的**子视图**（`#folder-view-tabs`，节点信息界面里也有同一套） |
| 默认父容器 | **没有**：目标随记录里写的 `父extKey` 走 | **当前文件夹**：对没写 `parentExtKey` 的记录补上它的 extKey |
| 误挂防护 | 无（记录指哪挂哪） | 当前文件夹**没有 extKey 就直接报错**，不允许"悄悄挂到根上" |
| 工具栏 | 通用工具栏 | 多一行「导入目标：`<文件夹名>`　`extKey = <值>`」（没有 extKey 时显示
「⚠️ 该文件夹没有 extKey」） |

一句话：**全局那个是"把包导进树"，节点那个是"把这些节点导到**这个文件夹**下面"**。

### 10.1 Tab 的四段

1. **来源与文件**：选文件 / 选目录 / 拖入。下方一行「📦 已载入 N 份包：`<文件名…>`」
   （**空态也会留一行**「📦 **未载入包**」，所以"这里会显示包名"一眼可预期；
   同一行还会附上一次导入的信息「✅ 上次导入：`<名>`（新增 x，更新 y[，失败 f]）」）。
2. **预览（dry-run）**：`新增 N · 更新 M · 跳过 K · 警告 W · 错误 E`
   - 每行可展开看**字段级 diff**（旧值 → 新值 → 采用的策略）
   - 警告与错误各自可筛选，扫一眼就知道 key 规范有没有破
   - **`▶ 执行导入` 那一行紧挨在统计栏正下方**（v8.4 调过位置：先看结论、再点执行）
3. **执行**：一次事务；完成后 toast 计数
4. **导入记录**：`source` / 时间 / 新增·更新·跳过 计数（存 `settings.autoImport.history`，只留最近 50 条）

**进度与预计时间（v8.4）**：读包与"解析出计划"**分阶段报进度**（面板上那行
`已用 … · 预计还需 …`，带 `data-phase/data-done/data-total`），每处理完一个文件就
`await yieldToUI()` 让出主线程 ⇒ **界面不冻**。
⚠️ **写入那一段不可分片**：`applyPlans` 是**一次事务**（要么全成、要么全回滚），
所以那里只报阶段名与记录条数并**如实标注"不可分片"**，不假装有百分比。

### 10.2 真正的「自动」

用 **File System Access API**（`showDirectoryPicker`）：

- 你授权一次「爬虫输出目录」，句柄存 IndexedDB（原生 IndexedDB，不走项目的数据层）；
- 之后定时轮询（间隔可配），发现新 crate → **载入为待执行**，不自动写；
- 可选开关「自动应用」：仅当预览里 **0 错误**（且警告数低于你设的阈值）时才自动执行；
- 权限过期 → 提示重新授权（必须由用户手势触发，不能静默重请求）。

**纯前端、零后端、零依赖**，符合本项目的形态。
不支持的浏览器自动降级为纯手动（只做文件选择）。

> 注意：浏览器无法常驻后台。所以「自动」的语义是
> **「页面开着时定时发现」**，不是「关掉浏览器也会同步」。

```
  5. 删掉某条的 extKey 再导     → 该条进 errors，其余照常
  6. 改一条 name 使其与另一条相似 → 出现 ⚠️ 警告，但两条都新建
  7. 只有 P、没有 C 的包（如 qoj_problems.json）→ 整批报"父节点不存在"，
     补一条 C 记录后重导成功
  8. 含 R 的包（如 qoj_submissions.json）→ 题目 status2 自动变准，
     且爬虫没有写任何状态字段
```

### 12.4 明确不做（防止后续被当成遗漏）

- **key 自动修正**：改了 key 就等于换了身份，会直接破坏幂等（4.8）；
- **相似度自动合并**：4.6 的硬约束；
- **整包回滚**：粒度是逐条（9.2）；
- **写回爬虫目录**：单向只读（决策 3）；
- **应用的隐式容器创建 / URL 推断**：2.3；
- **按列名猜语义**：7.3，语义一律由包内 `fieldMap` 显式声明。

**规则只有一份**：`core/siblingOrder.js`（`compareSiblings` / `orderedIds` / `orderChildren` / `treeOrder`）——
C 按开赛时间倒序、R 按提交时间倒序、年份层 S 按年倒序、**P 按题号升序**（`compareProblemId`）；混合类型一个字不动。
两个消费者：产包侧 `scripts/crate-merge.mjs`、应用侧 `features/AutoImport/apply.js`（导入后 `orderChildren`）。

不变量：
- **树序的真源是 `childOrder`**：手排（`handlers/H3_sort.js` 的题目/提交排序）与导入重排都写它。
  **任何"显示一份顺序"的地方都必须跟 `childOrder`**，不许自己再定第二套（哪怕那套"更整齐"）。
- `collectByType`（以及 `cProblemNodes` 里的 `psUnder`）本来就是按 `childOrder` **前序**遍历
  ⇒ **收集顺序就是树序**，（单根的）显示侧不需要再排一次。

坑：
- **`cProblemNodes` 无条件按题号重排卡片**：手动排出来的难度序在卡片上永远看不到（树变了、卡片不动）——
  `v9.0.2` 修的正是这个；`v9.0.7` 又把**判据**修对了：不是看"走过几个根"（`roots.length`），
  而是看「**存活的题**来自几个根」—— 组头的**成员副本**会被走一遍，但它们贡献的题**按组去重全被丢掉**，
  存活的题其实全来自组头自己（有树序）⇒ 按 `roots.length` 判会让"组头 + 成员"的比赛**整体退回题号序**
  （症状与 v9.0.2 一模一样：提示说已排序、树序也变了，**那一行方框一个都没动**）。
  真的跨子树时（成员独有的题）：**组头那份按它的树序在前**，成员独有的题按题号序垫底。
  回归测试：`src/test/cProblemOrder.test.js`。
- **每次导入都会重排所有容器**：`apply.js` 的 `orderChildren(draft)` 对**所有容器**重算 ⇒ 手排的顺序会被冲掉。
  `v9.0.3` 起用 **`manualOrder`** 兜住：手排过的容器（题目排序 / 提交记录排序 / 上移下移）导入时**跳过**；
  两种排序**都**各有一个"**恢复自动**"项（题目 = 题号升序；提交 = 提交时间倒序 —— 那正是 R 的规范序）
  = 清掉标记、交还给自动排序。
  `STRUCTURAL` ⇒ 导入包**写不进**这个键（包不许替本机决定要不要自动排）。
- **增删子节点**：`manualOrder` **不丢、不清**（`v9.0.4` 定的规则）—— 新来的孩子**追加在末尾**
  （`pushChild` 的既有行为），人排过的其余顺序原样保留，标记照旧。
  为什么不"集合一变就回到自动"：年份层 S 每次导入都会有新比赛进来，那样等于把 S 上的手排永久废掉。
  要回到自动只有一个口：那一项的「恢复自动」。
- **排序作用在"一支"上，不是单个 C**（`v9.0.4`）：`handlers/H3_sort.js` 收 `nodeId` = 这一支的根 ——
  子树下**每个"子节点里有题目"的容器**各排一次（在 C 上点 = 只排这一场；在 W/S/O 上点 = 排一整支，
  按钮标签写明「（这一支）」）。找容器靠**题目反查 `parentOf`**（那个索引在草稿里一直维护着，
  见 `ops/tree.js`/`ops/upsert.js`/`ops/synth.js`），别另写一遍走树。
- **排序前先看那一列有没有数据**：`ratio` 全空 / `cfDifficulty = 0`（= 未填）时排了也是白排
  ⇒ 明说"排不出"，别弹"已排序"。
